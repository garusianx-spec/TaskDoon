## Evidence and fixes

### Session restoration

The access token is memory-only. The existing browser client sends the HttpOnly refresh cookie
on the same-origin `/api/v1/auth/refresh` request and echoes the readable CSRF cookie. The cookie
names, scope, rotation, server authorization and expiry rules are unchanged.

The reproduced client bug was that temporary refresh failures resolved as no session, and a
workspace-load failure could also select sign-in after successful session restoration. The live
site's particular failing request was not inspected, so this does not assert a production cookie
or infrastructure cause.

Restoration now distinguishes invalid credentials from unavailable checks, retains the loading
gate while pending, and exposes the existing-design Persian retry screen. Sign-out has a local
intent marker and ignores late refresh responses. The socket reconnect path also handles a
temporarily unavailable refresh without treating it as confirmed revocation.

Local browser tests verify a hard refresh on `/more`, direct `/tasks`, unchanged URL and selected
authorized workspace, no sign-in flash, retry after a simulated 503, real server-confirmed session
expiry, revocation, and sign-out followed by refresh.

### Invitation department

The inherited form used fixed department identifiers and the request omitted `departmentId`.
The form now selects actual active-workspace IDs, sends the selected ID or `null`, and waits for
API confirmation. Failed validation retains form values. Integration tests verify the pending
invitation and accepted membership, reject a foreign-workspace department, and preserve email
invitations and invitations without a department.

### Invitation SMS

Creation previously confirmed only the invitation and transactional outbox entry. The worker
discarded the provider receipt. Neither creation nor a queue entry proved delivery.

The additive `0029_invitation_sms_attempts` migration stores attempt history and a sealed link on
the existing invitation. Historical invitations keep unknown delivery status. Retry reuses the
same invitation and link, checks permissions/rank/tenant/pending status, uses idempotency and a
row lock, and respects the existing configured API limits plus a 60-second per-invitation
cooldown and five-attempt cap. No route-level override weakens a stricter configured API limit.
Concurrent creation uses the existing normalized pending-invitation unique index.

The worker claims a queued attempt before sending. Duplicate job execution cannot resend it.
A timeout or ambiguous response remains unknown and does not enable resend. Confirmed transient
refusals can be retried; configuration, template, invalid-recipient and blocklist failures cannot.
Pending invitations retain their status and known reason per recipient, including mixed batches.

The SMS.ir delivery mapping follows the provider's public status table at
<https://app.sms.ir/developer/help/statusCode>, report contract at
<https://api.sms.ir/swagger/v1/swagger.json>, and official SDK report endpoint:
<https://github.com/IPeCompany/SmsPanelV2.DotNet>.

| SMS.ir delivery state                 | Interpretation                                                                           | Retry eligibility             |
| ------------------------------------- | ---------------------------------------------------------------------------------------- | ----------------------------- |
| 1 — Delivered                         | Confirmed delivered, after matching the report message ID and successful report envelope | No                            |
| 2 — Undelivered                       | Terminal handset-delivery failure                                                        | Yes, subject to server limits |
| 3 — ReachedTheOperator                | Intermediate; retain confirmed sending, continue report checks                           | No                            |
| 4 — NotReachedTheOperator             | Terminal operator failure                                                                | Yes, subject to server limits |
| 5 — ReachedTheProvider                | Intermediate; retain confirmed sending, continue report checks                           | No                            |
| 6 — Failed                            | Terminal provider failure                                                                | Yes, subject to server limits |
| 7 — BlackList                         | Terminal blocked recipient                                                               | No                            |
| 8, missing, null, or unfamiliar value | Unknown delivery; never infer failure or handset receipt                                 | No                            |

Reports are read-only SMS.ir requests scoped to tracked invitation attempts. They are queued with
a 60-second delay and at most 30 report checks, 60 seconds apart. Report exhaustion does not turn
provider acceptance into failure or delivery. The real BullMQ worker test verifies the delayed
job and its retry, advancing only the disposable test job's due time to keep the test fast.
